# Платформа сезонного хранения колёс — инструкция и план создания

> Внутренний сервис сети шинных центров. Версия 0.2 от 01.11.2026 (адресация приведена к текущей схеме: XX = склад).
> Статус: черновик для обсуждения. Помеченные **[решить]** пункты требуют решения руководителя.

---

## 1. Цели и границы

**Что делает платформа**

1. Принимает комплекты колёс/шин на хранение в любом магазине сети.
2. Присваивает хранению уникальный номер договора (печатается QR на бирках колёс) и адрес хранения `XX_YY_ZZ` (склад_ряд_ячейка).
3. Ведёт перемещения комплектов между магазинами и складами с полной историей: кто, когда, откуда, куда.
4. Готовит комплекты к выдаче (клиент записался на шиномонтаж → колёса привезли со склада в нужный магазин к дате).
5. Выдаёт комплект клиенту и закрывает хранение.
6. Обменивается данными с 1С:УТ 10.3 (клиенты, услуги, начисления, оплаты).

**Чего платформа не делает** (это остаётся в 1С)

- Деньги, касса, фискализация, взаиморасчёты, бухгалтерия.
- Справочник цен (цены берутся из 1С или задаются тарифом, согласованным с 1С).
- Продажа шин и дисков.

**Принцип разделения:** 1С — мастер по **деньгам и контрагентам**, платформа — мастер по **физическому хранению** (где лежит, в каком состоянии, кто перемещал).

## 2. Адресное хранение и идентификация

### 2.1 Как устроено сейчас (принято за основу)

- **Договор хранения** получает уникальный номер при создании хранения.
- На колёса клеятся **бирки** с основной информацией по хранению и **QR-кодом, в котором зашит номер договора**.
- Адрес места хранения: `XX_YY_ZZ`, где **`XX` — склад**, `YY` — ряд, `ZZ` — ячейка. Пример: `02_07_15` = склад 02, ряд 07, ячейка 15.

Платформа повторяет эту схему, ничего не ломая в текущей работе:

| Что | Чем определяется | Меняется ли |
|---|---|---|
| **Что хранится** | Номер договора (QR на бирке) | Никогда |
| **Где хранится** | Адрес `XX_YY_ZZ` | При каждом перемещении |
| **Где приняли** | Магазин приёма — реквизит договора | Никогда |

Адрес уникален во всей сети, потому что содержит код склада. При перемещении на другой склад меняется весь адрес (`02_07_15` → `03_01_04`), а договор и бирки остаются прежними, перепечатывать ничего не нужно.

### 2.2 Если по одному договору несколько комплектов

Бывает, что клиент сдаёт два комплекта (например, две машины или шины + диски отдельно), и они лежат в разных ячейках. Предлагаю:

- В QR по-прежнему номер договора, но с суффиксом комплекта: `000123/1`, `000123/2`. Если комплект один — суффикс можно не печатать (`000123` = `000123/1`).
- **[решить]** Нужна ли такая детализация, или у вас правило «один договор = один комплект»?

Для старых бирок без суффикса сканер просто находит договор и показывает все его комплекты.

### 2.3 Служебные (виртуальные) адреса

Комплект не всегда лежит в ячейке склада. Для таких состояний заводятся виртуальные локации:

| Код | Смысл |
|---|---|
| `М<код магазина>` | Буфер магазина (принят, ещё не отправлен на склад, или привезён к выдаче), например `М05` |
| `TR-<номер перемещения>` | В пути |
| `ISSUED` | Выдан клиенту (адрес освобождён) |

Если в каком-то магазине есть свой стеллаж для хранения, его заводят как склад со своим кодом `XX` — тогда адресация одинаковая везде.

### 2.4 Формат и ограничения адреса

- Регулярное выражение: `^\d{2}_\d{2}_\d{2}$`. До 99 складов, 99 рядов на склад, 99 ячеек в ряду.
- Если в ряду есть ярусы, нумеруйте ячейки сквозь ярусы (ярус 1: 01–20, ярус 2: 21–40) — формат сохраняется.
- **[решить]** Ёмкость ячейки: обычно 1 комплект (4 колеса). Если ячейка вмещает 2 комплекта — указать в справочнике (`capacity = 2`).

## 3. Основные понятия

| Понятие | Описание |
|---|---|
| **Локация** | Магазин или склад. Тип: `store` / `warehouse`. Магазин тоже может хранить (если есть место). |
| **Ряд, ячейка** | Физическое место хранения внутри локации. |
| **Клиент** | Владелец колёс. Связан с контрагентом 1С по GUID. |
| **Автомобиль** | Госномер, марка/модель. У клиента может быть несколько машин. |
| **Договор (квитанция) хранения** | Документ приёма: клиент, авто, магазин, срок, тариф, подписи/фото. |
| **Комплект** | То, что хранится: обычно 4 колеса (шины на дисках) или 4 шины. Опознаётся по QR на бирках (номер договора, при необходимости с суффиксом комплекта). Обычно один договор = один комплект. |
| **Позиция комплекта** | Отдельное колесо/шина: размер, бренд, сезон, остаток протектора, DOT, повреждения, фото. |
| **Перемещение** | Документ переезда одного или нескольких комплектов между локациями. |
| **Задание** | Поручение сотруднику: разместить, отобрать, подготовить к выдаче к дате, инвентаризировать. |
| **Журнал движений** | Неизменяемая история: каждое изменение адреса или статуса комплекта. |

## 4. Жизненный цикл комплекта (статусы)

```
ПРИНЯТ (буфер магазина)
   │  отправка на склад
   ▼
В_ПУТИ ──────────────► РАЗМЕЩЁН (ячейка XX_YY_ZZ)
                           │  клиент записался / запросил выдачу
                           ▼
                       ЗАКАЗАН_К_ВЫДАЧЕ
                           │  отбор и рейс в магазин
                           ▼
                       В_ПУТИ ──► ГОТОВ_К_ВЫДАЧЕ (буфер магазина выдачи)
                                       │  выдача клиенту
                                       ▼
                                    ВЫДАН
```

Дополнительные статусы: `ПРОСРОЧЕН` (срок хранения истёк, клиент не забрал), `УТИЛИЗИРОВАН`, `УТЕРЯН/РАСХОЖДЕНИЕ` (по итогам инвентаризации).

Правила:
- Выдать можно только из статуса `ГОТОВ_К_ВЫДАЧЕ` и только при отсутствии долга (проверка через 1С).
- Магазин выдачи может отличаться от магазина приёма.
- Каждый переход статуса пишется в журнал движений с пользователем, временем и устройством.

## 5. Модель данных (PostgreSQL)

Ниже — основные таблицы. Поля сокращены до значимых.

```sql
-- Локации: магазины и склады
location (
  id            serial PK,
  code          varchar(3) UNIQUE,      -- склады: '01'..'99' (= XX в адресе); магазины: 'М01'..
  name          text,
  type          text CHECK (type IN ('store','warehouse')),
  address       text,
  is_active     bool,
  onec_guid     uuid                    -- склад/подразделение в 1С
)

-- Ряды склада
storage_row (
  id            serial PK,
  location_id   int FK location,        -- склад; его code = XX в адресе
  row_no        varchar(2),             -- YY
  UNIQUE (location_id, row_no)
)

-- Ячейки
storage_cell (
  id            serial PK,
  row_id        int FK storage_row,
  cell_no       varchar(2),             -- ZZ
  address       varchar(8) UNIQUE,      -- 'XX_YY_ZZ', генерируется
  capacity      smallint DEFAULT 1,
  is_blocked    bool DEFAULT false,     -- сломана/занята под другое
  UNIQUE (row_id, cell_no)
)

client (
  id            uuid PK,
  onec_guid     uuid UNIQUE,            -- контрагент в 1С
  full_name     text,
  phone         text,                   -- нормализованный +7XXXXXXXXXX
  email         text,
  consent_sms   bool
)

vehicle (
  id            uuid PK,
  client_id     uuid FK client,
  plate         text,                   -- госномер
  make_model    text
)

storage_contract (
  id            uuid PK,
  number        text UNIQUE,            -- номер договора, как сейчас (зашит в QR бирок)
  client_id     uuid FK client,
  vehicle_id    uuid FK vehicle,
  store_id      int FK location,        -- магазин приёма (XX)
  accepted_at   timestamptz,
  paid_until    date,                   -- оплачено до
  tariff_code   text,                   -- код услуги в 1С
  status        text,                   -- открыт/закрыт/просрочен
  onec_doc_guid uuid                    -- документ в 1С
)

wheel_set (
  id            uuid PK,
  qr_code       text UNIQUE,            -- что зашито в QR бирки: '000123' или '000123/2'; не меняется никогда
  contract_id   uuid FK storage_contract,
  kind          text,                   -- 'wheels' (на дисках) / 'tires' (только шины)
  qty           smallint,               -- обычно 4
  season        text,                   -- зима/лето/всесезон, шипы
  size          text,                   -- 205/55 R16
  status        text,
  current_cell_id     int FK storage_cell NULL,
  current_location_id int FK location,  -- для буфера/транзита
  notes         text
)

wheel_item (
  id            uuid PK,
  set_id        uuid FK wheel_set,
  position      text,                   -- ПЛ/ПП/ЗЛ/ЗП
  brand_model   text,
  dot           text,
  tread_mm      numeric(3,1),
  rim_info      text,
  damage        text
)

photo (id, set_id, item_id NULL, url, taken_at, taken_by)

transfer (
  id            uuid PK,
  number        text UNIQUE,
  from_location int FK location,
  to_location   int FK location,
  status        text,                   -- создано/собрано/в_пути/принято/расхождение
  driver        text,
  created_at, shipped_at, received_at
)
transfer_line (transfer_id, set_id, scanned_out bool, scanned_in bool)

task (
  id, type,                             -- place/pick/prepare_issue/inventory
  set_id, location_id, due_date, assignee_id, status
)

-- Неизменяемый журнал — главный источник правды по истории
movement (
  id            bigserial PK,
  set_id        uuid FK wheel_set,
  at            timestamptz,
  user_id       int,
  action        text,                   -- accept/place/move/ship/receive/issue/...
  from_cell     varchar(8) NULL,
  to_cell       varchar(8) NULL,
  from_status   text, to_status text,
  transfer_id   uuid NULL,
  device        text
)

-- Интеграция с 1С (шаблон transactional outbox / inbox)
integration_outbox (id bigserial, event_type, payload jsonb, created_at, delivered_at NULL, attempts)
integration_inbox  (id, idempotency_key UNIQUE, payload jsonb, processed_at)

app_user (id, login, name, role, location_id)   -- роли: см. раздел 7
audit_log (id, at, user_id, entity, entity_id, diff jsonb)
```

Ключевые инварианты (проверяются в БД, а не только в коде):
- Ячейка не может содержать комплектов больше, чем `capacity` (триггер или проверка в транзакции с блокировкой строки ячейки).
- У комплекта в статусе `РАЗМЕЩЁН` обязательно есть `current_cell_id`.
- Записи `movement` только добавляются, не редактируются и не удаляются.

## 6. Процессы (как это работает в магазине и на складе)

### 6.1 Приём на хранение (магазин)

1. Продавец ищет клиента по телефону/госномеру (поиск в платформе + в 1С через API, если клиента нет).
2. Создаёт договор: авто, количество комплектов, тариф, срок.
3. По каждому колесу заполняет карточку: размер, бренд, протектор, повреждения; делает 2–4 фото комплекта.
4. Печатает бирки на колёса (основная информация по хранению + QR с номером договора) и квитанцию клиенту с тем же QR.
5. Комплект получает статус `ПРИНЯТ`, адрес `М<код магазина>` (буфер магазина).
6. Платформа отправляет событие в 1С → в 1С создаётся документ на услугу хранения для оплаты.

### 6.2 Отправка на склад (перемещение)

1. Система формирует перемещение «Магазин 01 → Склад Северный» из комплектов в буфере (вручную или по расписанию рейсов).
2. При погрузке водитель/продавец сканирует QR на бирках каждого комплекта → `В_ПУТИ`.
3. На складе кладовщик сканирует при приёмке. Несовпадения → статус перемещения `РАСХОЖДЕНИЕ`, уведомление ответственному.

### 6.3 Размещение (склад)

1. Система **предлагает** свободную ячейку на этом складе (`XX` = код склада): по умолчанию ближнюю к входу; для комплектов, которые скоро заберут, — ближе к зоне отгрузки.
2. Кладовщик сканирует QR на бирке, затем QR ячейки → `РАЗМЕЩЁН`, адрес `XX_YY_ZZ`.
3. Если положил не туда, куда предложили, — система принимает фактическую ячейку (главное — скан), но пишет отметку.

### 6.4 Подготовка к выдаче

1. Клиент звонит / записывается на шиномонтаж в магазин N на дату D.
2. Продавец находит договор и создаёт заказ на выдачу → задание «отобрать» на склад с крайним сроком D−1.
3. Кладовщик отбирает по адресу, сканирует, формирует перемещение «Склад → Магазин N».
4. Магазин принимает сканированием → `ГОТОВ_К_ВЫДАЧЕ`, клиенту SMS «колёса готовы».

### 6.5 Выдача

1. Продавец сканирует QR из квитанции клиента или ищет по телефону/госномеру.
2. Платформа запрашивает в 1С состояние оплаты (нет ли долга за продление срока).
3. Сканирует QR на бирках выдаваемых колёс (защита от выдачи чужих колёс) → `ВЫДАН`, ячейка освобождена.
4. Если клиент сразу сдаёт «другой сезон» на хранение — тут же оформляется новый договор (частый сценарий «переобулся — сдал летние»).

### 6.6 Перемещение между складами / магазинами

Тот же документ «Перемещение», любая пара локаций. Используется для разгрузки переполненного склада, закрытия склада, переезда магазина.

### 6.7 Инвентаризация

Задание по ряду/складу: кладовщик сканирует все ячейки подряд. Система сравнивает с ожидаемым и выдаёт отчёт: лишние, недостающие, не на своём месте.

## 7. Пользователи и роли

| Роль | Права |
|---|---|
| Продавец магазина | Приём, выдача, заказ к выдаче, приём перемещений в свой магазин |
| Кладовщик | Размещение, отбор, перемещения, инвентаризация на своём складе |
| Водитель | Сканирование при погрузке/выгрузке |
| Руководитель магазина | Всё по своему магазину + отчёты, исправление ошибок |
| Администратор | Справочники (локации, ряды, ячейки, тарифы), пользователи, интеграция |
| Сервисная учётка 1С | Только API интеграции |

Вход: логин/пароль, лучше — через доменную учётную запись (Active Directory / LDAP), если в сети есть домен.

                             ▼
                    ┌──────────────────┐
                    │  Веб-сервер      │  nginx, HTTPS (внутренний сертификат)
                    └────────┬─────────┘
                             ▼
                    ┌──────────────────┐        ┌───────────────┐
                    │ Backend API      │◄──────►│ PostgreSQL    │
                    │ (REST, JSON/XML) │        └───────────────┘
                    │ + фоновые задачи │        ┌───────────────┐
                    └────────┬─────────┘───────►│ Хранилище фото│ (диск / MinIO)
                             │                  └───────────────┘
                             ▼
                 ┌────────────────────────┐
                 │ 1С:УТ 10.3             │  внешняя обработка + регламентное
                 │                        │  задание опрашивает API
                 └────────────────────────┘

**Рекомендуемый стек** (внутренний сервис, небольшая команда):

| Слой | Выбор | Почему |
|---|---|---|
| Backend | Python 3.12 + FastAPI (или .NET 8, если в команде C#) | Быстрая разработка, автодокументация API (OpenAPI/Swagger) — удобно 1С-программисту |
| БД | PostgreSQL 16 | Надёжность, транзакции, JSONB для журнала интеграции |
| Фронтенд | React/Vue SPA, оформленный как PWA | Работает на ПК и на ТСД/смартфоне, сканирование камерой или встроенным сканером |
| Печать этикеток | Термопринтер (Zebra/TSC/Godex), 58×40 мм, ZPL/TSPL | Этикетки на шины должны выдерживать влагу и холод — берите полипропиленовые |
| Фоновые задачи | Встроенный планировщик (APScheduler) или Celery + Redis | Рассылки, просрочки, очистка |
| Развёртывание | Docker Compose на внутреннем сервере (рядом с 1С) | Просто обновлять и переносить |
| Резервные копии | `pg_dump` ежедневно + копия фото, хранить 30 дней, вне сервера | Обязательно |
| Мониторинг | Логи + простой healthcheck + уведомление в Telegram/почту при ошибках интеграции | |

**Связь со складами.** Если на складе нестабильный интернет — PWA должна уметь работать офлайн короткое время (очередь сканов в браузере, отправка при появлении связи). Это закладывается в этап 2.

## 9. Интеграция с 1С:УТ 10.3

### 9.1 Ограничения УТ 10.3, которые определяют схему

- УТ 10.3 — обычные формы, платформа 8.2 или 8.3 в режиме совместимости 8.2. **HTTP-сервисы в 1С при этом, как правило, недоступны**, расширения конфигурации — тоже.
- Встроенные объекты `ЧтениеJSON/ЗаписьJSON` работают только без режима совместимости 8.2 (платформа 8.3.6+). Зато `HTTPСоединение`, `ЧтениеXML/ЗаписьXML` и XDTO доступны всегда.

**Вывод — схема «1С ходит в платформу»:**

1. Платформа — REST-сервер. 1С — клиент.
2. В 1С работает **внешняя обработка** «Обмен с платформой хранения», запускаемая регламентным заданием (или обработкой по расписанию через отдельный сеанс) каждые 1–5 минут.
3. Платформа отдаёт данные в **JSON или XML** — по заголовку `Accept`. Для 1С в режиме совместимости 8.2 используем XML, для 8.3 без совместимости — JSON.
4. Связь объектов хранится в 1С без изменения конфигурации: через **«Дополнительные свойства» (ПВХ `СвойстваОбъектов`)** — свойство «ID хранения» у контрагента и документа. Конфигурация остаётся на поддержке.

### 9.2 Кто мастер каких данных

| Данные | Мастер | Направление |
|---|---|---|
| Контрагенты (клиенты) | 1С | 1С → платформа (+ платформа может создать нового клиента и запросить его создание в 1С) |
| Номенклатура услуг хранения, цены | 1С | 1С → платформа |
| Магазины/склады (подразделения) | 1С | 1С → платформа (сопоставление по GUID) |
| Договоры хранения, комплекты, адреса, перемещения | Платформа | платформа → 1С (события) |
| Начисления, оплаты, долги | 1С | 1С → платформа |

### 9.3 Поток обмена

```
Приём в магазине ──► платформа пишет событие contract.created в outbox
                              │
     1С (каждые N мин): GET /api/v1/integration/events?after=<последний id>
                              │
     1С создаёт «Реализацию товаров и услуг» (услуга хранения) / «Заказ покупателя»
                              │
     1С: POST /api/v1/integration/ack {event_id, onec_doc_guid}
                              │
Оплата в кассе 1С ──► 1С: POST /api/v1/integration/payments {contract, paid_until, сумма}
```

Гарантии:
- **Ни одно событие не теряется**: событие пишется в `integration_outbox` в той же транзакции, что и сам договор.
- **Повторная доставка безопасна**: каждый запрос от 1С содержит `Idempotency-Key`; повтор с тем же ключом возвращает прежний ответ.
- 1С сама хранит «последний обработанный id события» и при сбое просто переспрашивает.

### 9.4 Эндпоинты API (v1)

Аутентификация: HTTPS + заголовок `X-Api-Key` (отдельный ключ на сервисную учётку 1С), доступ только из внутренней сети. Документация — автоматически по адресу `/docs` (Swagger).

**Справочники (1С → платформа)**

| Метод | Путь | Назначение |
|---|---|---|
| `PUT` | `/api/v1/clients/{onec_guid}` | Создать/обновить клиента (ФИО, телефон) |
| `PUT` | `/api/v1/services/{onec_guid}` | Услуга хранения: код, наименование, цена за сезон/месяц |
| `PUT` | `/api/v1/locations/{onec_guid}` | Сопоставление подразделения/склада 1С с локацией |

**Запросы из 1С (чтение)**

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/v1/clients/search?phone=&plate=` | Найти клиента и его хранения |
| `GET` | `/api/v1/contracts/{number}` | Договор: комплекты, статус, адрес, оплачено до |
| `GET` | `/api/v1/sets/{qr_code}` | Комплект по QR бирки: статус, текущий адрес, история |
| `GET` | `/api/v1/stock?location=&status=` | Остатки на хранении (для отчётов в 1С) |

**Очередь событий (платформа → 1С)**

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/v1/integration/events?after={id}&limit=100` | Новые события |
| `POST` | `/api/v1/integration/ack` | Подтверждение обработки + GUID созданного документа 1С |

Типы событий: `contract.created`, `contract.extended`, `contract.closed`, `set.issued`, `set.overdue`, `transfer.completed`, `client.created` (новый клиент из магазина — 1С создаёт контрагента и возвращает GUID через `ack`).

**Деньги (1С → платформа)**

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/v1/integration/payments` | Оплата: договор, сумма, документ 1С, «оплачено до» |
| `PUT` | `/api/v1/contracts/{number}/debt` | Текущий долг клиента по договору (для блокировки выдачи) |

**Пример события (JSON):**

```json
{
  "id": 10452,
  "type": "contract.created",
  "created_at": "2026-11-01T12:30:05+03:00",
  "data": {
    "contract_number": "000123",
    "client_onec_guid": "8c1f…",
    "store_code": "М01",
    "store_onec_guid": "a77e…",
    "service_onec_guid": "51d0…",
    "sets": [
      {"qr_code": "000123", "kind": "wheels", "qty": 4,
       "season": "winter", "size": "205/55 R16", "address": "М01"}
    ],
    "paid_until": null,
    "amount": 4800.00
  }
}
```

**То же в XML** (для 1С в режиме совместимости 8.2):

```xml
<event id="10452" type="contract.created" created_at="2026-11-01T12:30:05+03:00">
  <contract_number>000123</contract_number>
  <client_onec_guid>8c1f…</client_onec_guid>
  <store_code>М01</store_code>
  <amount>4800.00</amount>
  <sets>
    <set qr_code="000123" kind="wheels" qty="4" season="winter"
         size="205/55 R16" address="М01"/>
  </sets>
</event>
```

**Коды ответов:** `200/201` — успех; `400` — ошибка данных (тело с описанием по полям); `401` — неверный ключ; `404` — не найдено; `409` — конфликт (например, ячейка занята, повторный ключ с другим телом); `5xx` — 1С повторит позже.

### 9.5 Что делает 1С-программист

1. Внешняя обработка обмена: HTTP-клиент, разбор XML/JSON, создание документов, запись «ID хранения» в доп. свойства.
2. Настройка регламентного запуска (или запуск по расписанию через отдельный сеанс 1С).
3. Отправка оплат: обработчик после проведения документа оплаты (или выборка оплат при каждом сеансе обмена — без изменения конфигурации).
4. Журнал обмена в 1С (регистр сведений или просто лог-файл) для разбора ошибок.

Оценка: 5–10 рабочих дней для опытного 1С-программиста.

## 11. Оборудование и разметка

- **Бирки на колёса:** формат как сейчас — основная информация по хранению и QR с номером договора. Если будете заказывать новые: полипропилен, термотрансферная печать, клей для холода; добавить позицию колеса (ПЛ/ПП/ЗЛ/ЗП).
- **Этикетки ячеек:** ламинированные, QR с адресом `XX_YY_ZZ` и крупный текст адреса. На торце ряда — табличка «Склад XX · Ряд YY».
- **Сканирование:** на складе — ТСД на Android (Urovo, Zebra, Mertech) или смартфон; в магазине — ручной сканер USB.
- **Принтеры:** по одному в каждом магазине и на каждом складе.

## 12. Безопасность и надёжность

- Доступ только из внутренней сети/VPN; HTTPS везде.
- Персональные данные клиентов (ФИО, телефон, госномер) — это ПДн по 152-ФЗ: согласие на обработку в квитанции, ограничение доступа по ролям, журнал действий.
- Резервные копии ежедневно, проверка восстановления раз в квартал.
- Удаление данных — только «мягкое» (пометка), история движений неизменяема.
